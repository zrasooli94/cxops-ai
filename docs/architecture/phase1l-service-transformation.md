# Phase 1L — Service Transformation Analytics

Status: **IMPLEMENTED** (pending final review) · Phase: 1L · Depends on: Phase 1C.3D
observability tenant isolation, Phase 1D.2 authorization, prior service-operations
and agent-observability work

## Objective

Give operators a production **service transformation** readout: ticket volume,
responsiveness, SLA health, AI adoption, specialist usage, human workload and
estimated value realization — each computed over a **7/30/90-day window** and
compared against an **equal-length previous period**. A single tenant-scoped
read endpoint serves the data, and a new control-center **Transformation**
workspace renders it with a window switcher. No new capabilities, no new
specialists, no LLM calls, and no invented/subjective KPIs are introduced; the
numbers come entirely from existing persisted production data.

### Scope guardrails (applied)

- **Read-only analytics.** One `GET` endpoint; no mutation surfaces added.
- **No new capability.** The route reuses `ticket.read` for visibility and
  authorization, exactly like the shared service-operations data.
- **No fake metrics, no LLM calls.** Every number is derived from persisted
  tables; no summary is generated by a model.
- **No employee ranking.** Workload is aggregate message/reply counts only.
- **No SLA/policy changes.** Escalation and SLA behavior is untouched; this
  layer only reports it.

## Route & authorization

`GET /api/backend/service-operations/transformation` — `app/api/routes/service_operations.py:107`

- `response_model=ServiceTransformationSummary`
- Requires `ticket.read` via the shared `RequireCapability` dependency.
- `days: Annotated[int, Query(le=90, ge=7)] = 30` — out-of-range days are
  rejected by FastAPI (422); a second explicit guard restricts to the bounded
  `{7, 30, 90}` literal set.
- Tenancy resolved by `CurrentTenant` *before* capability resolution (inherited
  from Phase 1C.3D / 1D.2).
- Records a Prometheus counter via `record_service_transformation_request()`
  (`app/core/metrics.py:426`).

## Window semantics

`days` selects the current window `[now − days, now)`; the previous period is
the equal-length span `[now − 2·days, now − days)`. Every metric except the
explicit snapshot fields is window-bounded. **Current-state snapshot fields are
explicitly all-time** (documented decisions):

- `service_volume.currently_open` / `currently_needs_response` — all open
  tickets org-wide, regardless of creation date.
- `queue_breakdown[*].{due_soon, breached}` — derived from **current unresolved
  escalation rows per queue** (not ticket SLA fields), so an old unresolved
  breach still counts in current state. This is why windowed expectations alone
  cannot reproduce these numbers.
- `queue_breakdown[*].{open_tickets, needs_response, priority_urgent_high,
  assigned_tickets}` — current state.

Window-bounded metrics include `tickets_created`, `tickets_resolved`,
`resolved_in_window`, first-response/resolution analytics, SLA breaches buckets
(`breached_in_window` / `due_soon_in_window` / `triggered_in_window`),
`reopened_in_window`, agent-run counts, specialist workflow paths, human-workload
counts, channel conversation/message counts, and the ROI measurement.

## Metric sections (`ServiceTransformationSummary`)

### Service volume
`tickets_created`, `tickets_resolved` (window), `currently_open`,
`currently_needs_response` (current state).

### Service performance
Average/median first-response minutes and resolution minutes for tickets
resolved within the window. Values are real measured durations, never guesses.

### SLA health
`first_response_sla_breaches` / `resolution_sla_breaches` (`breached_in_window`),
`total_sla_breaches`, `due_soon` and `escalation_count` (windowed),
`escalation_rate = triggered_in_window / created · 100`, `reopened_tickets`
(distinct in window), `reopen_rate = reopened / resolved · 100`. All rates are
emitted on a 0–100 scale.

### AI adoption (windowed, from persisted agent runs)
`tickets_analyzed_by_ai` (distinct tickets with at least one run), `agent_runs`,
`autonomous_executions`, `human_approval_required` (excludes runs whose
`authorization_source == "policy_auto"` — automatically-authorized runs are the
autonomous envelope, not the human-approval queue), `human_approved`,
`human_rejected`, `successful_agent_executions`, `failed_agent_executions`,
`no_action_runs`, plus `ai_analysis_rate`, `autonomous_execution_rate`,
`human_approval_rate`, `execution_success_rate` (0–100 scale).

### Specialist usage (windowed)
Per-run `specialist_paths` are projected to run counts: `coordinator_runs`,
`knowledge_specialist_runs`, `action_specialist_runs`, plus
`knowledge_usage_rate` (any knowledge hop), `pure_action_route_rate`
(action without knowledge), and `invalid_specialist_path_count` (malformed
orderings). No employee-level detail is exposed.

### Human workload
`human_messages_sent` and `ai_executed_replies` for the window — aggregate
counts only.

### Value realization (ROI)
Reproduced through `AgentObservabilityService.roi_summary` for the window:
`estimated_minutes_saved`, `estimated_hours_saved`, `estimated_labor_savings_usd`,
`agent_ai_cost_usd`, `estimated_net_savings_usd`, `roi_percent`. The formal ROI
is only emitted on **measured** autonomous execution from instrumented runs;
`pricing_configured`, `measurement_status`, `minimum_autonomous_samples`, and
`sample_size_sufficient` carry the guardrail state, and `roi_percent` stays
`null` until the minimum sample is reached. No invented per-ticket savings.

### Queue breakdown
Per queue: current-state workload (`open_tickets`, `needs_response`, `due_soon`
current-state, `breached` current-state, `priority_urgent_high`, `assigned_tickets`)
plus windowed `resolved_in_window`, `agent_runs`, `autonomous_executions`.

### Channel breakdown
Conversations and messages per support channel for the window, with a
0–100 `percentage` share of conversations.

### Comparisons
A flat map of current-vs-previous for every scalar metric present in both
periods: `current`, `previous`, `absolute_change`, and `percent_change` (only
when previous ≠ 0 — no division by zero, no invented deltas).

## Opportunity signals (deterministic rules)

Derived from current-window data only, labeled by signal + scope: (constants at
`app/services/service_transformation_service.py:39–54`)

| Signal | Scope | Condition |
|---|---|---|
| `sla_pressure` | queue | `due_soon + breached >= 10` |
| `ai_adoption` | queue | `agent_runs >= 8` and `autonomous_rate < 0.20` |
| `ai_adoption` | organization | `agent_runs >= 8` and `autonomous_rate < 0.20` |
| `knowledge_utilization` | organization | `agent_runs >= 6` and `knowledge_usage_rate < 50` |
| `approval_backlog` | organization | `human_approval_required >= 5` |
| `reopen_risk` | organization | `reopen_rate >= 15` and `reopened_tickets >= 5` |

Each signal carries only persisted evidence and a fixed, generic suggested
focus. Signals are sorted by `(signal, scope_key)`. There are **no LLM-authored
recommendations** and no subjective KPI.

## Implementation notes

- Repository (`app/repositories/service_transformation_repository.py`) queries
  use explicit `.select_from(Ticket)` before `.outerjoin(...)` for the snapshot
  and queue-breakdown queries — without it SQLAlchemy raised
  `InvalidRequestError: Don't know how to join to <Subquery>`.
- Escalation current-state derivation lives in
  `ServiceEscalationRepository.escalation_current_by_queue`; windowed SLA
  buckets in `windowed_summary_for_tenant`.
- Service composition in `app/services/service_transformation_service.py`; the
  schema in `app/schemas/service_transformation.py`.
- `mypy` requires `int(row._mapping["count"])` (a `func.count()` label collides
  with `Row.count`); no type-ignore lines are used.

## Exclusions (by design)

- No CSAT/FCR/sentiment/overall-score fields — added no new subjective KPIs.
- No new specialists or routing changes (specialist *usage* is reported, not
  altered).
- No SLA/escalation policy changes.
- No employee-level workload ranking.
- No CSAT-FCR inventory of missing data; the endpoint reports what persisted
  data supports and withholds rates/savings it cannot measure.
